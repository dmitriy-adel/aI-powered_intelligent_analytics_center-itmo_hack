# aI-powered_intelligent_analytics_center-itmo_hack

![Mascot](img/mascot_dark_wide.png "Mascot")

## Описание проблемы 

Служба по связям с общественностью и государственными органами ежедневно тратит 3–4 часа на ручной мониторинг информационного поля. Специалисты вручную просматривают десятки СМИ, сайты регуляторов, Telegram-каналы и отраслевые дайджесты, чтобы выявить:
    - упоминания компании и конкурентов;
    - изменения в нормативно-правовой базе;
    - отраслевые тренды и кризисные сигналы.

Информация разрознена, саммари создаются вручную, а решения принимаются с задержкой. В рамках проекта требуется провести автоматизацию сбора данных и их анализа, после чего разработать . Решение нужно обернуть в удобный web-интерфейс, которым будет удобно пользоваться.

## Описание решения 

Согласно ТЗ, принято решение разработать систему автоматического поиска, сбора, обработки и представления информационных сообщений. В саму систему интегрирован графический интерфейс в виде web-приложения, который предоставляет пользователю возможность ознакомиться с найденными информационными сообщениями, провести их фильтрацию и сортировку, изменить их наполнение, а также сформировать отчет по хранимым информационным сообщениям. Отчеты формируются с использованием LLM

## Описание данных 

В рамках кейса не предоставлено исходных данных, ввиду чего мы занялись их сбором самостоятельно. Поскольку у нас не было времени на проведение разметки, данные для валидации собирались вручную и валидировались через генеративные LLM (Claude, GPT). Таким образом получена валидационная выборка для скрипта определения релевантности новости. Через аналогичный подход формирования выборки тестировались некоторые гипотезы, требующие оценки ЦА, к которой у нас не было доступа

Список обрабатываемых источников получен в рамках ТЗ. Разработанное решение позволяет добавить новый источник в краткие сроки

## Структура проекта 

Проект разделен на несколько зон:

    1. Парсеры. Через парсеры системы получает информационные сообщения. На текущий момент обрабатывается только текстовый канал информационных сообщений - ТГК, НПА, ленты новостных агентств. Обработка информационных сообщений из ТГК и других типов источников разделена на 2 инстанса, поскольку для обработки информационных сообщений из ТГК требуется включенный VPN, а при включенном VPN получить доступ к НПА не представляется возможным. Парсинг происходит в многопоточном режиме, что позволяет значительно уменьшить время, затрачиваемое на получение новостей

    2. Обработка информационных сообщений. После того, как сообщения были получены, они проходят предобработку. В частности, каждому информационному сообщению присваивается свой уровень релеватности, большая языковая модель оценивает последствия для заказчика относительно обрабатываемой новости и т.д. После чего информаицонное сообщение заносится в БД для дальнейшего использования

    3. Формирование отчетов. Ночью пайплайн собирает два типа брифов из уже обработанных новостей в базе, а не из сырого потока. Сначала отбрасываются сообщения с нулевой релевантностью и остаются только те, у которых скор коллеги (NER и TF-IDF, с учетом упоминаний самой компании, конкурентов, компаний похожего типа и значимых сущностей) выше 0,5. Затем скрипт забирает верх выборки по убыванию скора и только этот короткий список передается языковой модели: полный поток слишком велик и быстро переполнит контекст. Модель не пересказывает все подряд, а выбирает десять самых важных для компании пунктов с бизнес-значением. Ежедневный бриф считается за вчерашние календарные сутки и хранится за последние семь дней. Еженедельный - отдельно, за последнюю полную календарную неделю с понедельника по воскресенье. Более широкое окно для daily, например семь дней вместо суток, и динамический набор новостей до лимита контекста пока не включали: период в обсуждении не зафиксирован окончательно, поэтому начинаем с суток и фиксированного потолка выборки

    4. Графический интерфейс. Через графический интерфейс пользователь видит все новости, обработанные системой. по умолчанию они отсортированы в порядке убывания релевантности и дате публикации. Каждый источник представлен своей отдельной лентой, в которой отображаются все новости источника. При этом в интерфейсе системы предусмотрена общая лента, в которой хранятся наиболее релевантные новости, НПА и те информационные сообщения, что пользователь самостоятельно добавил в ленту. Через веб-интерфейс пользователь может редактировать новости, удалять их и добавлять новые ; изменять статус обрабатываемых источников, устанавливать периодичность запуска процесса парсинга источников, менять наполнение обрабатываемых источников ; формировать отчеты по информационным сообщениям за установленный промежуток времени.

## Гипотезы, от которых мы отказались

В этом разделе представлено несколько гипотез, от которых мы отказались во время работы над решением

- Сбор видео-данных. Проблема информационных сообщений средств массовой информации заключается в их субъективности. Взгляд на одну и ту же новость может быть совершенно разным в зависимости от редактора, что писал саму новость, и от новостного агентства, которое эту новость публиковало. Также при обработке новостей нет возможности провести качественный анализ реакции общественности на обрабатываемый материал, что может сильно исказить итоговую картину. Мы вывели гипотезу, согласно которой обрабокта видео-контента со специализированных сайтов (YouTube) позволит проводить более полный и подробный информационный анализ, но после общения с заказчиком от этой идеи мы отказались

- Проводить классификацию информационных сообщений на предмет наличия информации об угрозах информационной безопасности. Компания-заказчик специализируется, в том числе, на защите контента, что не имеет сильной связи с, непосредственно, ИБ. Гипотеза оказалась далека от реальности

- Использование графов для хранения и поиска информации. Реализация на скорую руку не принесла желаемых результатов, и практически ничем не отличалась от классического подхода. Принято решение сфокусироваться на более важных аспектах ИС

## Представление решения

Ниже описано, как устроены те части решения, которые отвечают за нормативно-правовую базу, устранение дублей и работу большой языковой модели. Эти компоненты дополняют общий пайплайн, уже описанный в разделе о структуре проекта.

    1. Сбор нормативно-правовых актов. В отличие от новостных лент, документы НПА не снимаются как обычные HTML-страницы СМИ. Система обращается к официальным реестрам: порталу проектов нормативных актов, системе обеспечения законодательной деятельности Государственной Думы, официальному интернет-порталу правовой информации и ленте правительства. Для каждого источника используется устойчивый идентификатор документа - номер законопроекта, идентификатор проекта на regulation.gov.ru либо номер официального опубликования. За счет этого одна и та же норма может быть прослежена по стадиям, а не заново распознаваться при каждом появлении в ленте

    2. Дедупликация информационных сообщений. Единицей хранения для системы является не отдельная перепечатка, а сущность: долгоживущий нормативный акт либо новостной сюжет. Сначала из публикации извлекаются устойчивые идентификаторы. При точном совпадении новая публикация присоединяется к уже существующей сущности как очередное событие в ее жизненном цикле. Если идентификатора нет, система строит векторное представление текста моделью text-embedding-3-small (OpenAI, через OpenRouter) и ищет ближайшие уже известные сущности. Если обращение к модели эмбеддингов недоступно, используется запасной локальный вариант на хешированных n-граммах, чтобы склейка не останавливалась. В спорных случаях пара кандидатов передается языковой модели, которая решает, идет ли речь об одном и том же объекте. Намеренно не используется более дешевый автоматический классификатор вместо этой проверки: ошибка склейки двух разных актов обходится дороже дополнительного обращения к модели

    3. Использование большой языковой модели. Языковая модель применяется после сбора и первичной оценки релевантности. Она формирует фактический заголовок, краткое содержание, поля "кто / что / когда", описание последствий и оценку влияния новости на компанию-заказчика. По итогам сравнения нескольких моделей в качестве основной выбрана DeepSeek V4 Flash. На валидационной выборке, размеченной вручную по материалам заказчика, она совпала с экспертной оценкой релевантности на всех проверенных карточках, работает быстрее более крупных открытых моделей и не завышает среднюю важность так, как это делает gpt-oss-120b. Модель gpt-oss-20b оставлена как запасной вариант

    4. Составление брифа. Бриф не строится по сырому потоку. Скрипт читает уже собранные и обработанные новости из базы, отсекает нулевую релевантность и берет сообщения со скором выше 0,5. В этот скор уже входят упоминания компании, конкурентов, компаний похожего типа и найденных в тексте значимых сущностей, поэтому отдельный второй классификатор перед моделью не нужен. Основная нагрузка по фильтрации и ранжированию лежит на существующем классификаторе: в модель уходит только верх выборки, а не полные тексты всех новостей. Пока период daily - вчерашние сутки, weekly - понедельник-воскресенье последней полной календарной недели. Число новостей на вход модели ограничено фиксированным потолком с учетом окна контекста и средней длины новости; динамически наращивать список до безопасного лимита контекста пока не стали. Модель получает отобранные материалы и собирает десять пунктов, фокусируясь на событиях с бизнес-значением для компании. Готовые брифы пишутся в таблицу reports: ежедневные за последние семь дней, плюс один недельный за прошлую календарную неделю. Счет идет ночью в пайплайне

    5. Стоимость использования модели. На разметку одной новости в среднем уходит около двух тысяч токенов. Фактическая стоимость обращения составляет порядка 0,00015–0,00022 доллара за карточку. Обработка тысячи сообщений - менее чем в четверть доллара. Формирование ежедневного и еженедельного отчета добавляет одно-два обращения за ночь и на общем фоне незаметно. Таким образом стоимость языковой модели не является ограничивающим фактором: узким местом остаются качество отбора релевантных сообщений и корректная склейка дублей, а не бюджет на вызовы API


## Технологический стек 

При реализации решения мы не выходили за рамки технологического стека, используемого компанией. Бэкенд написан на Python, фронтенд - JS + CSS + HTML, БД - PostgreSQL. Для быстрой развертки системы используется Docker
